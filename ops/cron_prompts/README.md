  同日用 `cron_update` 修订了质量标尺中的**段落长度一行**：原写「中位 110~130 字符」，与仓库实测（10-19 ≈200、10-20 ≈179、10-21 ≈318、10-23 ≈350 字符）不符，容易把句子拆碎；改为「中位落在 200~350 字符即可，与仓库现状一致」，并把判据明确为「每段是否讲清一件事、有没有出现 1 段成节」。**一切量化标准先对齐用户验收过的样本实测分布，不要自创更严的数字。**

- **2026-10-27 12:40**：两条日更提示词同步加入「⚡ 省 token 纪律」小节，并把 12:00 提示词一并入库。
  **动因**：实测 10-27 两条任务的 token 消耗——12:00 腾讯文档 72 轮模型调用、Σ 上下文 **1289 万**、Σ 输出 9.7 万、耗时 32.4 分钟；12:15 仓库 59 轮、Σ 上下文 **881 万**、Σ 输出 8.7 万、耗时 15.6 分钟。
  **根因不是上下文窗口大小，而是「每轮工具调用都要把整个上下文重送一遍」**（59~72 轮 × 平均 15~18 万 token）。窗口设 1M 而实际只用 24 万，缩窗口一个 token 都省不下来。
  **纪律内容**：① 原始内容（RSS/HTML/JSON/API 响应/历史日报全文/`get_content` 回显）一律在 bash 内用 python 解析完，只 print 结论行；② 检索 2~3 轮封顶，`web_search` 的 count 压到 4~5（8 条结果可吃 15k+ token）；③ 同阶段动作压进一个 bash（gist PATCH+校验、3 次 PUT+校验、全部收尾断言各压一轮）；④ 收尾断言压成 1 轮、记忆沉淀用一次 `memory_topic_append`；⑤ 写完先本地自检再提交；⑥ 12:00 额外加「MDX 提交前跑标签配平 + 敏感路径扫描」（避免为试 `/etc/resolv` 类内容过滤白烧 20+ 轮）。
  **预期**：两条合计 Σ 上下文从 2170 万降到 500~700 万量级（-65%~-75%），输出量基本不变。

- **2026-10-27 20:10 同日实测（一次手动试跑）**：用一次性任务 `456907181761105` 触发新版 prompt 的 12:15 那条（`session.mode=new`、agent/model/project 与正式 cron 相同），**禁提交仓库、只写本地**，跑完即删该任务。
