### ⚡ 省 token 纪律（2026-10-27 起）

**成本机制**：每多一轮工具调用＝把整个上下文重送一遍。实测 10-27 早上本任务 72 轮，把上下文重读了 **1289 万次**；同日 20:10 用带本节的版本试跑：20 轮、Σ 上下文 280 万、耗时 12.8 分钟。**唯一有效的省法是「减少轮次」+「不让大块原文进上下文」；缩小上下文窗口一个 token 都省不下来。**

1. **原始内容不进上下文**。抓 RSS / HTML / JSON、`smartcanvas.read` / `get_content` 的回显、历史文档全文，一律**在一个 bash 里用 python 解析完，只 print 结论行**。`get_content` 单篇回显 1.5~2.9 万字符，**读 3 篇就是 4 万 token 起** ⇒ 查重只抽「一级标题 + 小节标题 + 来源域名」骨架，需要核对具体数字时再单独取那一段。解析失败只 print 前 1500 字符 + 报错，**绝不 print 全文**。
   ⚠️ **抓取源限量 + 必须并发**：单轮 bash 抓的源 **≤ 15 个高价值源**，**用 `ThreadPoolExecutor` 并发抓**（串行抓 40+ 源会撞 bash 280 s 超时，**超时 = stdout 全空 = 白烧一整轮上下文**）。单源 8 s 超时，整轮 bash ≤ 60 s。**源不够就少抓，不要靠加量。**
   ⚠️ **腾讯文档 connector 调用同样限量**：`manage.folder_list` 在**一个 bash 内一次翻完**；`get_content` **最多读 3 篇**且只抽骨架（标题 / 小节标题 / 来源域名），要引用具体数字时再单独取那一段。**不要为每篇文档各起一轮。**
2. **检索 2~3 轮封顶**。第 1 轮：一个 bash 抓完全部低成本通道（RSS 源 + 官方 JSON + EDGAR + 状态页）并筛成摘要。第 2 轮：一次 `web_search`（count=4~5，查询词具体）。中文确有必要再补 1 轮。**`web_search` 命中会把整篇正文塞进上下文 ⇒ count 压到 4~5。**
3. **一轮能做完的绝不拆多轮**：`folder_list` 翻页 + 3 篇骨架抽取、标签配平自检 + 敏感串扫描、`create_smartcanvas_by_mdx` + `move_file` + 归位点验，各压进一个 bash。
4. **⚠️ MDX 提交前必须本地预检（10-27 实测踩坑）**：在 bash 内跑「标签配平 + 敏感字符串扫描」。payload 含 `/etc/passwd`、`/etc/resolv` 这类路径会被服务端**秒拒**（0.7 秒、空 stdout、报 `connector_provider_error`）—— **命中就改写措辞**（如「读取容器的 DNS 解析配置」）后重新生成。**绝不要靠反复提交去试探**：实测白烧 20+ 轮上下文。
5. **收尾压成 1~2 轮**：一个 bash 内跑完全部断言（标签配平、图标数、H2/H3 数量、来源域名去重、归位计数），一次 print；记忆沉淀用**一次** `memory_topic_append`。


### 第二步：整理为 MDX

按主线分类：模型端 / 监管端 / 算力端 / 产业与产品 / 资本与人事，按重要性排序。

#### MDX v2.1.0 强制规范（违反将导致整篇渲染失败）

**颜色一律用 token 枚举名，禁止任何 hex / rgb / CSS 颜色名。**

- `Mark color` → TEXT_COLORS：default, grey, blue, sky_blue, green, yellow, orange, red, rose_red, purple
- `Callout blockColor` / `Mark backgroundColor` → BLOCK_COLORS：default, grey, light_grey, dark, light_blue, blue, light_sky_blue, sky_blue, light_green, green, light_yellow, yellow, light_orange, orange, light_red, red, light_rose_red, rose_red, light_purple, purple
- `Callout borderColor` → BORDER_COLORS：default, grey, blue, sky_blue, green, yellow, orange, red, rose_red, purple
- `Divider blockColor` → DIVIDER_COLORS（多一个 black）

**⚠️ BORDER_COLORS 没有 light_ 变体。** 写 `borderColor="light_orange"` 会被静默降级为绿色。

常用配色（已验证）：主线/导语 `light_yellow`+`yellow`；日常提示 `light_blue`+`blue`；热点/利好 `light_green`+`green`；警示/争议 `light_red`+`red`；资本/战略 `light_orange`+`orange`。

其他硬性规则：
- 属性名是 `blockColor` / `borderColor`，**不是 `bgColor`**
- 行内样式一律 `<Mark>`，禁止 `**bold**` / `*italic*` / `<b>` / `<i>`
- 属性值必须双引号；布尔属性不写值（`<Mark bold>` 而非 `bold="true"`）
- 块级组件三段式多行 + 4 空格缩进，禁止写成一行
- Mark / Link 必须单行同行，禁止软换行
- 表格只能用 Table / TableRow / TableCell
- 列表每个 item 单独一个 BulletedList / NumberedList 组件
- frontmatter 仅允许 title / cover / icon / fontFamily / fontSize / spacing；默认值一律省略
- 正文开头不得重复 frontmatter.title
- 禁止未定义组件、ESM、MDX expression

**⚠️ 提交前必须做标签配平自检**：`Callout` / `BulletedList` / `BlockQuote` / `Mark` / `Table` / `TableRow` / `TableCell` / `ColumnList` / `Column` 各标签开闭数量必须相等，不配平先修正再提交。历史上曾因标签不配平导致整篇创建失败。

**MDX 规范补充（2026-10-19 实测，违反会直接导致整篇创建失败）**：

- **不要用 `<Paragraph>` 包裹内容**：仅当需要段落级属性（textAlign、blockColor）时才用 Paragraph；普通内容直接写纯文本。`smartcanvas.read` 的回显会自动包上 `<Paragraph>`，那是服务端序列化产物，**不要照抄回显当源文件写**
- **`<Table>` 无任何属性**：不要写 `readonly`（服务端会自己加）。整张表可用 `smartcanvas.edit` 的 `UPDATE` 增行改文案
- **单段落且无属性的引用块用 Markdown 的 `>` 表达**，不要用 `<BlockQuote>` 组件；多段落或嵌套时才用组件
- **缩进单位固定 4 个空格**：块级组件的内容行缩进 = 开标签缩进 + 4，子块开标签缩进 = 父块开标签缩进 + 4；禁止块级嵌套却无缩进
- **块级组件必须三段式多行**，禁止一行写完（`<Heading level="1">标题</Heading>` 是错的）
- **frontmatter 必须是文档第一段**，前面连空行都不能有
- **动手前先读官方规范文件**：`/workspace/.plugin-cache/**/skills/tencent-docs/smartcanvas/mdx_references.md`（版本随插件变，以文件实际内容为准），不要凭记忆写

#### 归日口径（全档唯一，不得自选）

**唯一规则：以事件的公开发布时间归属，落到北京时间那一天。**

- 判据是**事件公开那一刻**的时刻：换算成北京时间落在哪一天，就归哪一天
- 正文必须标注**发布方的原始发布时间**（美东 X 日下午/夜间发布写「美东 X 月 X 日」或「X 月 X 日晚间」）
- **校准锚点**：太平洋 10:00 = 北京当日 02:00 → 归**当日**；太平洋 12:00 之后 = 北京次日 → 归**次日**
- 媒体转载日**不作为归属依据**，只作为发现线索；中文转载日通常比事件日晚 1~2 天
- **不按「每日早报」的日期落笔** —— 中文聚合站的「某日分组」整组都可能是前 2~3 天的旧闻晨间汇总
- 录用通知 / arXiv v1 时间戳 ≠ 事件日（只能证明「不晚于该日」）
- 判定优先级：原文 URL 日期路径 > 通讯社电头 > 官方博客/newsroom > 权威媒体首发 > 聚合站时间戳 > 中文转载日
- **⚠️ OpenAI / Anthropic 官方页与 RSS 的 `datePublished` 被归一化到太平洋零点**，只能定发布方当地日期，不可当真实时刻；这类条目按「**发布方当地日期 + 1 天**」保守处理（美国厂商多在美国工作日白天 = 北京当日深夜到次日；**中国机构按当地日，不 +1**），正文注明依据是「官方标注日」。**OpenAI 官方 RSS**（`openai.com/news/rss.xml`）带精确到分的 GMT pubDate，是判 OpenAI 事件归日最省事的通道
- **⚠️ arXiv OAI 的 `<datestamp>` 是「记录里最新版本」的公布日，只有「仅 v1」的论文才等于 v1 公布日**；用之前先 `curl -sL https://arxiv.org/abs/<id> | grep -oE '\[v[2-9]\]'` 查有无后续版本
- **凡来源日期落在「稿件日 − 1」的官方页、且没有更强时刻证据的，一律按「官方标注日 + 1 天」复查**

**每日文档顶部必须逐字使用下面这一行口径声明：**

> 归档口径：<Mark color="blue">按事件公开那一刻的发布时间归属</Mark>——正文标注发布方的原始发布时间，换算成北京时间落在哪一天就归哪一天；转载日不作归属依据，旧闻重推须回官方渠道核过再收录。

**边界情形裁定：**

| 情形 | 归属 |
|:--|:--|
| 美东当日凌晨到上午的发布 | 归**北京时间当日**（换算后仍在当日） |
| 美东当日下午到深夜的发布 | 归**北京时间次日**，正文标注「美东 X 月 X 日」 |
| 官方当日发，路透次日报道 | 归**官方发布那一刻换算出的北京时间日** |
| 官方当日发，中文站数日后转载 | 同上，**转载日不作依据** |
| 聚合站把 2~3 天前的旧闻当当日头条重推 | 剔除，回官方渠道核过真实发布日 |
| 官方无日期，仅聚合站有 | 标注 `<Mark color="orange">日期存疑</Mark>` 并**移出正文**，只在审计说明留辨析句 |
| 事件横跨多日（如法案推进） | 归**首次实质进展日** |

**「标注 ≠ 修正」——这是历史高频失败模式务必避免：** 发现日期冲突时加一句「存疑」标注却仍按错误一方写入正文，等于没修。处置只能二选一：1. 回到官方渠道判定，按官方发布时间归档；2. 官方确实无法判定 → 该条移出正文，只留一句辨析说明两方日期差异。

**同一条事件不得在两篇文档各写一遍。** 发布前用 `grep` 扫 `/workspace/ai_daily/*.md` 确认无跨篇重复收录。

#### 动手前的必做检查

**第一步永远是查重，不是新建。**

1. `manage.folder_list`，参数 `folder_id` 填**该日期所属年份的子目录**（2026 年填 `MVrRaosFFGat`）。**必须翻完所有页** —— 返回体有 `finish` 字段，为 `false` 时给 `start` 加上本页实际返回条数继续翻，只看第一页会漏数据

**抓取窗口的固有特征。** 12:00 北京 = 00:00 美东，因此 D 日文档实际覆盖「北京时间 D 日 00:00–12:00」+「美东 D-1 日 09:00–23:59」。由此：
- D 日文档里出现 D-1 日美东发布的事件**属正常，不是跨篇重复**，不得据此误删
- 美东 D 日下午到夜间的发布要到 D+1 的文档才被收录，这是结构性特征，调时间无法消除
- 若某事件按归日口径应归 D+1，就写进 D+1 的文档

### 第三步：写入腾讯文档

依次调用：
1. `create_smartcanvas_by_mdx`，参数 `content_format`="mdx"、`title`="<YYYY-MM-DD> AI 大事件汇总"、`mdx`=完整 MDX
2. `manage.move_file`，参数 `file_id`=上一步返回、`target_folder_id`=**该日期所属年份的子目录 id**（2026 年为 `MVrRaosFFGat`），**不是根目录**

若 MCP 工具未直接注入，用 `mcode-tools connector call "<tool_name>" --args-file <json>` 调用。

**⚠️ 归位结果怎么判定（本项目反复踩过的坑）：**

- `move_file` **常返回 `connector_provider_error` 但实际已生效**，不要据此判定失败
- `manage.query_file_info` 的 `status` 字段**不可信**：`status: "hidden"` 时文档可能实际已在目标目录内。曾出现连续 4 次 `move_file` 全部报 failed、但 `folder_list` 计数已 +1 且目标目录确实包含该文档的情况，此时盲目重试只会浪费时间
- **计数必须现算，不要复述历史数字。** 归位前扫一次目录拿基线，归位后数一次，差 +1 才算生效；目录列表里能直接命中该 `file_id` 同样算归位成功。

**唯一可信判据：`manage.folder_list` 计数**。move 之后等约 10 秒，翻完目标子目录所有页看条目数是否 +1（或直接确认该 file_id 是否在列表里）
- 若计数未变再重试，最多 3 次、间隔 6~10 秒；仍失败则照常交付链接并说明未归位，**不要重建文档**（会产生孤儿文档）

**⚠️ 工具名注意**：`get_content` **不带 `document.` 前缀**，正确是 `connector__tencentdocs__get_content`；写成 `document.get_content` 会报 "tool is not available"。`search_file` 的参数键是 `search_key` 不是 `keyword`。

## 补全：当天文档已发布后才发现漏收（2026-10-19 新增）

**不要重建。** 重建会换掉 `file_id` 与文档链接，目录里还会多出一份同名文档。用 `smartcanvas.edit` 原地改：
- `INSERT_AFTER` + `id`（锚点块 id）→ 在该块后插入多块内容
- `UPDATE` + `id` → 替换该块内容（`<Table>` 整张也能改，readonly 只锁子元素）
- `DELETE` + `id` → 删除该块
- 锚点 id 从 `smartcanvas.read` 的回显里取（每个块都有 `id="..."`）；回显会自动注入 id、自动包 `<Paragraph>`、自动给 `<Table>` 加 readonly，**只取 id 和结构，不要照抄回显当源文件**
- 补条目后必须同步改五处，否则文档自相矛盾：导语里的条数与摘要、关键数据速览表、审计说明的「原生 / 补录」双栏、剔除清单的逐条依据、末尾「主要来源」
