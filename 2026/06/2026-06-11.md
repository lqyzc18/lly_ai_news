# 2026-06-11 AI 大事件

北京时间 2026 年 6 月 11 日（星期四）。谷歌在美东 6 月 10 日开源了 DiffusionGemma，第一次把扩散机制带进文本生成的开源大模型；同一天 OpenAI 与甲骨文宣布战略合作，把模型调用直接接进 OCI 的既有承诺额度。国产侧，小米 MiMo 团队发布并开源终端 AI 编程助手 MiMo Code，把 1 万亿参数级自研模型和 Agent 框架绑在一起卖。合规面还有一条被路透社捅出来的消息：微软因 Claude Fable 5 的数据留存新规，在公司内部禁用了这款模型。

## 1. 谷歌与英伟达开源 DiffusionGemma：文本不再一个 token 一个 token 地写

美东 6 月 10 日，谷歌发布实验性开源模型 DiffusionGemma，并与英伟达合作完成针对显卡与数据中心的优化。这是谷歌首个面向本地部署的开放权重扩散式文本模型，构建在 Gemma 4 家族之上，吸收了 Gemini Diffusion 的研究思路，发布说明中署名的研究者包括 Brendan O'Donoghue 与 Sebastian Flennerhag。

它换掉了自回归的生成方式：模型不从随机占位 token 出发逐个预测，而是像图像扩散模型那样，从一整块随机 token「画布」开始反复迭代精修，每次前向并行输出 256 个 token，并用双向注意力让每个 token 互相关注。官方给出的吞吐是：单张 NVIDIA H100 上每秒超过 1000 个 token，RTX 5090 上超过 700 个 token，在专用 GPU 上整体比同规模自回归模型快最多 4 倍。模型为 26B 参数的混合专家（MoE）架构，推理时仅激活 3.8B，量化后可放进约 18GB 显存的消费级显卡，权重以 Apache 2.0 协议在 Hugging Face 公开，支持 vLLM、Transformers、MLX 与 Unsloth，官方 llama.cpp 支持「即将到来」。

谷歌对它的定位是速度优先而不是质量优先：官方明确表示整体输出质量低于标准版 Gemma 4，需要最高质量的场景仍建议用自回归的 Gemma 4。理由是自回归模型在云端依靠批量请求能跑得很高效，但在本地单用户场景下硬件利用率很低，扩散式生成则是把更大的工作量一次性交给处理器。厂商认为这类「全区块感知」特性对行内编辑、代码填空、数独求解、氨基酸序列处理等非线性、结构化任务更有优势。英伟达则把模型在 RTX 5090、4090 上做了量化，并在 Hopper 与 Blackwell 系统上以 NVFP4 优化性能。

## 2. 小米开源 MiMo Code：终端里的 Coding Agent 与 1 万亿参数底座

6 月 11 日，小米 MiMo 技术团队发布并开源探索性 AI 编程助手 MiMo Code V0.1.0，这是小米 MiMo 首次进入 Coding Agent 领域。工具基于开源项目 OpenCode 二次开发，运行在本地终端环境而非云端 IDE 插件，采用 MIT 协议开源，原生适配 Windows、Linux、Mac。

架构上它用 Main Agent 加 checkpoint-writer subagent 的双智能体协作：把任务执行与信息记录拆开，状态保存交给独立 subagent，当上下文窗口接近上限时自动重建一份精简简报，让主 Agent 无缝续跑而不是从头开始。配套的还有项目记忆、会话检查点、任务进度三重机制，以及定期由独立 Agent 读取历史会话做合并、去重、验证和压缩的 /dream 命令。小米为自研模型设计了专属 Harness 系统，并提供 Compose 模式：按 Tab 切换后输入一个想法，系统自动走完设计、规划、编码、测试、审查全流程。小米团队把它概括为「前期重规划、后期稳验证」，官方给的对比案例是「用 Golang 实现一个支持 redis-cli 连接的 Redis」——Claude Code 较快生成可运行代码但测试覆盖不足，MiMo Code 前期规划更久、最终功能更完整、测试更详细。

模型侧，MiMo Code 内置限时免费的多模态模型 MiMo-V2.5，并支持接入 DeepSeek、Kimi、GLM 等主流模型与第三方 Token Plan；语音输入由 MiMo-V2.5-ASR 支撑。MiMo-V2.5-Pro 的公开规格是总参数 1.02 万亿、混合专家架构、单次推理激活 420 亿参数、支持 100 万 token 上下文、可稳定支撑近千轮工具调用，小米称其性能可比肩 Claude Sonnet 4.6。

跑分需要分开看：按小米公众号文章披露的对照测试（同一个 MiMo 模型下比较 Agent 系统），MiMo Code 在 SWE-bench Pro 上为 62%、Claude Code 为 57%，Terminal Bench 2 上为 73%、Claude Code 为 68%，SWE-bench Verified 为 82% 对 76%。这些是厂商自测数据，无第三方复现。小米大模型事业部技术总监的说法是，相同模型条件下分数差距完全来自 Agent 协同架构的优化。资本背景上，小米 2026 年一季度业绩报告称 AI 是投入力度最大的领域，今年 AI 领域至少投入 160 亿元，雷军宣布未来三年在 AI 领域投入 600 亿元。

## 3. 微软因数据留存新规限制员工使用 Claude Fable 5

6 月 11 日，据路透社报道，微软已对内部员工使用 Claude Fable 5 作出限制。微软已向 GitHub Copilot、Microsoft Foundry 平台的付费客户开放该模型服务，但并未把它纳入内部版 GitHub Copilot 的可用模型清单；Anthropic 旗下其他 Claude 模型在微软内部仍可正常使用，这类模型执行零数据留存规则。

争议的焦点是 Fable 5 配套的数据留存机制：该模型搭载全新的安全分类系统，要求留存用户交互数据，用户提问内容与模型生成结果都会被保存，常规数据在 30 天后删除，若内容被判定违反平台规则，相关问答数据最长可留存两年。微软法务部门正在对 Anthropic 最新数据留存条款做全面评估，出于企业机密、内部信息安全与合规考量，暂未批准该模型在公司内部落地。这条限制也把 Anthropic 自己此前公开的谨慎姿态摆到台面上：公司曾坦言 Mythos 系列在网络安全领域能力突出、全面开放存在潜在风险，因此为 Fable 5 增设了多重提问防护机制，而这套机制带来的数据留存规则随之成为行业争议点。

## 4. OpenAI 与甲骨文达成战略合作：OCI 用户可直接用云承诺额度调用模型

美东 6 月 10 日，OpenAI 与甲骨文宣布建立战略合作伙伴关系，核心是打通 AI 模型调用与云基础设施的协同通道。具体安排是从未来数周开始，Oracle Cloud Infrastructure 的客户无需再走冗长的新增采购审批流程，即可直接用已有的甲骨文云承诺额度（UCM 积分）访问 OpenAI 的前沿模型与 Codex 系统。

这一安排的产品逻辑是降低企业把前沿 AI 接入既有工作流的门槛：已经在用 Oracle 云的企业可以直接消耗原有承诺额度，而不必新开预算和采购流程。放在 OpenAI 多云布局的语境下看，这也是其云端算力伙伴结构的一次扩容——此前微软与亚马逊是主要算力供应商，而 OpenAI 与微软的独家协议在 4 月已修订为非独家，公司正在为上市做基础设施层面的多元化。
